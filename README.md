# EKMS — Foundation, Authentication, UI and Vocabulary

English Knowledge Management System is a multi-user English learning product. This repository contains Phase 01 infrastructure, Phase 02 authentication, the Phase 03 UI foundation, and Phase 04 personal vocabulary management. The curated IELTS catalog, learning, Writing, mastery, dashboard, AI Tutor, and Web3 are not implemented. The approved [product specification](https://docs.google.com/document/d/17rny6Cr5BgZ3q_pS7MFjx97LjRXEvXKxUtOhYp4ogMA/edit) governs later work; Appendix D v1.4 takes priority for changed business rules.

## Architecture and layout

`apps/web` is the Next.js presentation shell. Semantic design tokens live in `apps/web/src/app/tokens.css`; reusable controls and layout live in `apps/web/src/components`. The UI is documented in `docs/UI_FOUNDATION.md` and ADR 0005. `apps/api` is the NestJS REST authority. `apps/worker` is an independent NestJS process with a BullMQ connection but no business jobs. `packages/config` validates environment values. `packages/contracts` holds shared response contracts. PostgreSQL is durable state; Redis is queue/cache infrastructure. See `docs/adr` for decisions.

The browser uses same-origin `/api/v1` requests forwarded by Next.js. The Docker build compiles that rewrite with the internal `http://api:3001` address; a host build defaults to `http://localhost:3001`. API health routes are `GET /api/v1/health/live` and `GET /api/v1/health/ready`. Liveness only checks the process. Readiness checks both PostgreSQL and Redis and returns 503 if either is unavailable. API success responses use `{ "data": ... }`; errors use `{ "error": { "code", "message", "requestId" } }`. `X-Request-Id` is generated by the server for every request.

## Requirements

- Node.js 24.13.1 (`.nvmrc`) and pnpm 11.25.0.
- Docker Engine and Compose for the isolated local stack. PostgreSQL and Redis are **not** exposed on host ports.
- Ports 3000 (Web) and 3001 (API) available on loopback, or set `WEB_PORT` and `API_PORT` in `.env`.

Versions are pinned in manifests and `pnpm-lock.yaml`. Do not use `latest` images or install from an unfrozen lockfile in CI.

## Setup and local development

1. `pnpm install --frozen-lockfile`
2. Copy `.env.example` to `.env`, replace the local database password, and generate two **independent** 32-byte base64 secrets for `JWT_SIGNING_KEY_B64` and `REFRESH_PEPPER_B64` (for example, `openssl rand -base64 32` run separately twice). Set exact browser origins and cookie mode. Never commit `.env`. The local `.env` is for Compose interpolation and host-side tooling; Compose injects service-network URLs into containers.
3. `docker compose config --quiet` to validate configuration.
4. `docker compose up --build -d` to start this project's isolated stack. Compose project name is `ekms-p01-foundation`. It creates only its own `postgres_data` volume and does not use older EKMS volumes.
5. `docker compose ps` and `curl -i http://127.0.0.1:3001/api/v1/health/ready` to verify health; visit `http://127.0.0.1:3000` for the shell.

For a hybrid workflow, start only `postgres` and `redis` with Compose and provide host-accessible database/Redis URLs through your local `.env` or an approved tunnel. Database and Redis ports are intentionally not published by default. Then run `pnpm --filter @ekms/api dev`, `pnpm --filter @ekms/worker dev`, and `pnpm --filter @ekms/web dev` in separate terminals. Do not add host port mappings to shared infrastructure without reviewing exposure.

## Quality commands

`pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm test:integration`, and `pnpm build` run quality checks. Authentication integration tests require the isolated `ekms_p02_test` PostgreSQL database and an explicit `DATABASE_URL` pointing to it; they refuse any other target. They create and remove only their own users. `pnpm db:validate` validates the Prisma schema, while `pnpm db:status` checks migration history against the configured database. Run database-connected commands only after confirming the target is an isolated EKMS database.

For focused UI checks, run `pnpm --filter @ekms/web test`, `pnpm --filter @ekms/web typecheck`, and `pnpm --filter @ekms/web build`. Real-browser visual smoke is in `research/evidence/phase03-visual-smoke.cjs`. Install its pinned test tools outside the repository with `npm install --prefix /tmp/ekms-p03-browser --no-save --no-package-lock --ignore-scripts playwright@1.63.0 axe-core@4.11.0`, then run `NODE_PATH=/tmp/ekms-p03-browser/node_modules node research/evidence/phase03-visual-smoke.cjs`. The script requires the running local stack at port 3000, a cached compatible Playwright Chromium binary, and the owned EKMS development database for temporary-user cleanup. Set `EKMS_BROWSER_ORIGIN=http://localhost:3000` when using a host-run Next.js development server. It captures sanitized temporary-account screenshots under `research/evidence/phase03-visual/` and never prints credentials or tokens.

For local HTTP integration, create `ekms_p02_test` once inside this Compose project's PostgreSQL service, migrate that database, then run the suite with the test URL. The test setup uses higher rate limits so its repeated login assertions do not throttle unrelated cases; it still verifies account-oriented 429 behavior at its configured threshold:

```bash
docker compose exec -T postgres sh -lc 'createdb -U "$POSTGRES_USER" ekms_p02_test'
docker compose run --rm --no-deps api sh -lc 'export DATABASE_URL="${DATABASE_URL%/*}/ekms_p02_test?schema=public"; pnpm --filter @ekms/api exec prisma migrate deploy'
docker compose run --rm --no-deps -e REDIS_URL=redis://redis:6379/1 -e AUTH_LOGIN_IP_LIMIT=100 -e AUTH_LOGIN_ACCOUNT_LIMIT=7 -e AUTH_REGISTER_IP_LIMIT=100 -e AUTH_REFRESH_IP_LIMIT=100 api sh -lc 'export DATABASE_URL="${DATABASE_URL%/*}/ekms_p02_test?schema=public"; pnpm test:integration'
```

Skip the first command if that database already exists. Confirm Redis logical database 1 is unused before running the test command; the test suite uses it to keep rate counters separate from development traffic. `node research/evidence/phase02-proxy-smoke.mjs` checks same-origin cookie propagation against the running local stack and removes only the temporary user it creates.

The `.env.example` IP limits of 100 requests per hour are local development settings. Requests through the Next.js proxy share the API socket peer address, so this bucket is shared by local users; the account login limit remains 5 attempts per hour. A multi-user deployment needs a reviewed trusted-ingress design before tuning IP limits. Do not trust arbitrary `X-Forwarded-For` headers. A real Chromium smoke is available at `research/evidence/phase02-browser-e2e.cjs`; install Playwright in an isolated test environment and supply it through `NODE_PATH` when running that script. It creates and removes its own test user.

The Phase 01 baseline migration remains intact. Phase 02 adds the reviewed `User`, `RefreshSession`, and `SecurityEvent` schema and migration. After confirming the target is this project's isolated development database, run `docker compose exec -T api pnpm --filter @ekms/api exec prisma migrate deploy` and then `docker compose exec -T api pnpm --filter @ekms/api db:status`. Do not run `prisma migrate reset` or `docker compose down -v` against any database containing data. The worker starts and connects to Redis but does not process a production job.

## Authentication

The entry page links to `/auth`; successful login opens `/app`, an authenticated landing page. `/account` lists active sessions and offers revoke, logout, and logout-all. Registration creates an account but requires a separate login. All auth mutations require an `Origin` matching `AUTH_ALLOWED_ORIGINS`; configure the exact browser origin, including port. The access token is kept in memory, and the HttpOnly refresh cookie restores a session after reload. If refresh reuse is detected, the whole token family is revoked. The browser does not store tokens in local or session storage. See [ADR 0004](docs/adr/0004-authentication-and-session-security.md) for session, cookie, CSRF, rate-limit, and multi-tab decisions.

Endpoints are `POST /api/v1/auth/register`, `login`, `refresh`, `logout`, `logout-all`; `GET /api/v1/auth/sessions`, `GET /api/v1/me`; and `DELETE /api/v1/auth/sessions/:id`. Successful responses use `{ "data": ... }`; errors use `{ "error": { "code", "message", "requestId" } }`. Never paste token or cookie values into logs or support chats.

## Operations and troubleshooting

### Personal vocabulary (Phase 04)

Authenticated users can open `/vocabulary` to add their own target meanings, optional source context and notes, organize personal tags, search and filter, and archive or restore a sense. Adding a word does not create a learning attempt or mastery score. Source context is optional and empty input becomes null. Exact recognized senses and exact manual canonical definitions deduplicate per user; a different meaning under the same lemma remains separate. See [ADR 0006](docs/adr/0006-vocabulary-identity-and-rights.md) for identity, concurrency, cursor, and rights decisions.

The UI can show original local example senses when the user explicitly requests them. No licensed live dictionary is configured. Without one, lookup reports unavailable and manual add continues to work. These examples are not the curated IELTS catalog. User-authored meanings and context remain private; any future curated or licensed content requires its own provenance and rights review.

The owner-scoped REST API includes `GET /api/v1/dictionary/lookup?q=…`, `POST/GET /api/v1/vocabulary`, `GET/PATCH /api/v1/vocabulary/:id`, `POST /api/v1/vocabulary/:id/archive` and `/restore`, and `GET/POST /api/v1/tags`, `PATCH/DELETE /api/v1/tags/:id`. The optional `provider=fixture` lookup is development only. POST mutations require a UUID `Idempotency-Key`; edits and archive/restore require `expectedVersion`. Lists default to 20 active items, cap at 100, and return an opaque `nextCursor` for stable pagination. All private resource IDs are checked with the authenticated owner ID.

Phase 04 adds the additive `20261021_p04_vocabulary` migration. Confirm the database target and backup before `prisma migrate deploy`; never use reset or destructive volume cleanup. The real-browser vocabulary test is `NODE_PATH=/tmp/ekms-p03-browser/node_modules node research/evidence/phase04-browser-smoke.cjs` against the owned local stack. It creates and deletes only temporary test users and writes screenshots to `research/evidence/phase04-visual/`. The local benchmark is `node research/evidence/phase04-benchmark.cjs`; it creates and deletes one temporary user. Neither script is a production load test.

- `docker compose ps` shows service and health state; `docker compose logs api worker` shows structured startup/request events. Logs exclude request bodies, headers, queries, and connection URLs.
- API liveness healthy but readiness 503 means PostgreSQL or Redis is unavailable. Check only this Compose project's services. The response deliberately omits dependency and credential details.
- If Docker reports WSL integration unavailable, enable integration for this distro in Docker Desktop, then rerun `docker version` and `docker compose version`.
- If a port is occupied, choose a free loopback `WEB_PORT` or `API_PORT` in `.env`; container ports stay fixed.
- If Prisma reports an invalid URL, inspect variable **names and formatting** without pasting credentials into chat or logs.

## Security and Git

Only `.env.example` is tracked; real secrets and generated artifacts are ignored. Browser code never receives database, Redis, or provider credentials. Run future migrations against a confirmed development target with a backup plan. Implement on authorized feature branches only. Do not push or merge directly into `master`/`main`, force push, or deploy without separate approval. Phase evidence is in `research/PHASE_REPORTS` and `research/evidence`.
